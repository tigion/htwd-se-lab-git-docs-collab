=== 1. Änderungen und Versionen verwalten

. Die folgenden Aufgaben behandeln den Umgang mit *Änderungen* und *Versionen*
(Commits) im lokalen Arbeitsverzeichnis.

- *Änderung* ... (noch) nicht versionierte Änderung im lokalen Arbeitsverzeichnis
- *Version* ... versionierte Änderung (Commit) im lokalen Arbeitsverzeichnis

==== Aufgabe 1.1 - Versionen untersuchen

Untersuchen Sie in Ihrem lokalen Repository Unterschiede zu früheren Versionen
und wechseln Sie temporär zu einem früheren Projektstand.

. Vergleichen Sie mithilfe von `diff` verschiedene Commits bzw. Änderungen.
+
.Hinweise: `diff`
[%collapsible]
====
=====
Mit dem Befehl `diff` werden die Unterschiede zwischen zwei Versionen (Commits)
oder zum lokalen Arbeitsstand angezeigt. Ein `+` steht für eine hinzugefügte und
ein `-` für eine entfernte Zeile. Änderungen innerhalb einer Zeile werden mit
einer Kombination aus `-` und `+` dargestellt.

----
$ git diff <1>
$ git diff <file> <2>

$ git diff --cached <3>

$ git diff <commit> <4>
$ git diff <commit> HEAD <5>
$ git diff <commit-1> <commit-2> <6>

$ git diff <branch-1> <branch-2> <7>
----
<1> zeigt Unterschied der letzten Version (_HEAD_) zum lokalen Arbeitsstand
<2> mit der zusätzlichen Angabe `<file>` kann gezielt eine Datei oder ein
    Verzeichnis verglichen werden
<3> mit `--cached` werden die vorgemerkten Änderungen gegenüber `HEAD` oder
    einer angegebenen Version verglichen
<4> zeigt Unterschied der Version `<commit>` zum lokalen Arbeitsstand
<5> zeigt Unterschied der Version `<commit>` zur letzten Version `HEAD`
<6> zeigt Unterschied von Version `<commit-1>` (älter) zur Version
    `<commit-2>` (neuer)
<7> zeigt Unterschied von Branch `<branch-1>` zu Branch `<branch-2>`
=====
====

. Wechseln Sie mit `switch` (oder `checkout`) zu einem älteren Projektstand und
  kehren Sie danach wieder zum aktuellen Stand zurück.
+
.Hinweise: `switch` (modernere Variante zu `checkout`)
[%collapsible]
====
=====
Mit dem Befehl `switch` kann zwischen Branches gewechselt werden. Mit der Option
`--detach` kann außerdem ein bestimmter Commit ausgecheckt werden, ohne auf
einen Branch zu wechseln.

Zum aktuellen Stand kann man mit `git switch <branch>` zurückkehren. Ein
Wechsel zu einem älteren Commit verändert die Historie nicht. Zwischenzeitliche
Commits auf den vergangenen Projektstand erscheinen nicht mehr in der Historie,
sind aber kurzzeitig über https://git-scm.com/docs/git-reflog[`git reflog`]
wiederherstellbar.

// TODO: Grafik für switch anpassen
image::grafik_git_switch-detach.png["...",width=251]

----
$ git log --oneline <1>
$ git switch --detach <old_commit> <2>
$ git switch main <3>
----
<1> Versionshistorie (Commits) anzeigen; die Option `--oneline` erlaubt eine
    Anzeige mit einer Zeile pro Commit.
<2> Zum vergangenen Projektstand wechseln. Dabei befindet sich `HEAD` im
    sogenannten __Detached-HEAD__-Zustand und zeigt direkt auf den Commit.
<3> Zum aktuellen Projektstand (__main__-Branch) zurückkehren.
=====
====
+
.Hinweise: `checkout`
[%collapsible]
====
=====
Mit dem Befehl `checkout` wird der Arbeitsbereich auf den Zustand einer
bestimmten Version (Commit) oder eines Branches gesetzt.

Zum aktuellen Stand kann man mit `git switch <branch>`, neuere Alternative zu
`git checkout <branch>`, zurückkehren. Zwischenzeitliche Commits auf den
vergangenen Projektstand erscheinen nicht mehr in der Historie, sind aber
kurzzeitig über https://git-scm.com/docs/git-reflog[`git reflog`] wiederherstellbar.

image::grafik_git_checkout.png["...",width=251]

----
$ git log --oneline <1>
$ git checkout <old_commit> <2>
$ git switch main <3>
----
<1> Versionshistorie (commits) anzeigen, die Option `--oneline` erlaubt eine
    Anzeige mit weniger Details auf einer Zeile pro Commit
<2> vergangenen Projektstand laden
<3> Zu aktuellem Projektstand (__main__-Branch) zurückkehren.

NOTE: In der unteren Statusleiste (links) in VS Code oder über das git-Kommando
`git branch` sieht man den aktuellen Branch, bspw. _main_. Seit Oktober 2020
verwenden alle auf GitHub neu erstellten Repositories `main` anstelle von
`master` als Standard-Branch (https://github.com/github/renaming[Quelle]).
=====
====

==== Aufgabe 1.2 - Änderung wegspeichern

. Nehmen Sie in Ihrem Repository eine lokale Änderung vor und speichern Sie diese
temporär mit `stash` weg. Schauen Sie sich Ihren lokalen Arbeitsstand an.
. Stellen Sie anschließend Ihre weggespeicherte Änderung wieder her und nehmen
Sie diese als neue Version auf.

.Hinweise: `stash`
[%collapsible]
====
=====
Mit dem Befehl `stash` lassen sich Änderungen im lokalen Arbeitsverzeichnis
vorübergehend speichern und bei Bedarf später wiederherstellen. Dies ist
hilfreich, wenn eine begonnene Arbeit unterbrochen oder kurzfristig der Branch
gewechselt werden soll, ohne die aktuellen Änderungen als Commit zu speichern.

image::grafik_git_stash.png["...",width=625]

----
$ git stash <1>
$ git stash push <2>

$ git stash pop <3>
$ git stash apply <4>

$ git stash drop <5>

$ git stash list <6>
stash@{0}: WIP on main: ...
stash@{1}: WIP on main: ...
stash@{2}: On main: Arbeitsstand X

$ git stash show <7>
$ git stash show -p <8>
----
<1> `git stash` ist eine Kurzform für `git stash push`.
<2> Änderungen an verfolgten (*tracked*) Dateien werden im Stash gespeichert
    und aus dem Arbeitsverzeichnis entfernt und im Stash abgelegt
<3> `pop` ... stellt die gespeicherten Änderungen wieder her und entfernt den
    zugehörigen _Stash_.
<4> `apply` ... stellt die gespeicherten Änderungen wieder her und behält den
    zugehörigen _Stash_ (nützlich, wenn die Änderungen noch an anderer Stelle,
    z.B. in einem anderen _Branch_, benötigt werden).
<5> `drop` ... entfernt den _Stash_ mit den enthaltenen Änderungen.
<6> `list` ... zeigt eine Liste der vorhandenen _Stashes_.
<7> `show` ... zeigt eine Übersicht der Änderungen im _Stash_ gegenüber der
    aktuellen Version.
<8> `show -p` ... zeigt die konkreten Zeilenänderungen im Patch-Format.

NOTE: Hat man mehrere Stashs, wird bei `pop`, `apply` und `drop` der zuletzt
angelegte genommen. Man kann auch den gewünschten Stash mit bspw. `git stash
pop stash@{1}` angegeben. Der neueste ist `stash@{0}` (default), der
nächstältere `stash@{1}` und so weiter.

.Optionen für `git stash [push]`
[cols="3,4,10"]
|===
| Option | Langform              | Beschreibung

| `-m "<message>"`
| `--message "<message>"`
| Gibt dem erzeugten Stash eine Beschreibung bzw. einen Namen. `git stash -m "<message>"` (`git stash save "<message>"` ist die veraltete Variante.)

| `-u`
| `--include-untracked`
| Speichert zusätzlich *untracked* Dateien im Stash.

| `-S`
| `--staged`
| Speichert nur *staged* Änderungen im Stash.

| `-k`
| `--keep-index`
| Behält *staged* Änderungen im Arbeitsverzeichnis und speichert nur *unstaged* Änderungen im Stash.
|===

.Status von Dateien und Änderungen in Git
[cols="1,3"]
|===
| Status      | Beschreibung

| `tracked`   | Dateien, die unter Versionskontrolle stehen
| `untracked` | Neue Dateien, die noch nicht unter Versionskontrolle stehen

| `staged`    | Änderungen im Index, die zum Commit vorgemerkt sind
| `unstaged`  | Änderungen an *tracked* Dateien, die noch nicht zum Commit vorgemerkt sind
|===

==== Aufgabe 1.3 - Änderung verwerfen

Nehmen Sie in Ihrem Repository eine lokale Änderung vor und verwerfen Sie diese
anschließend, ohne eine neue Version zu erstellen.

.Hinweise: `restore` (`checkout`), `reset`, `clean`
[%collapsible]
====
=====
image::grafik_git_checkout-reset-clean.png["...",width=381]

----
$ git restore -- <file> <2>
$ git checkout -- <file> <1>
$ git reset --hard <3>
$ git clean -df <4>
----
<1> Setzt lokale Änderungen einer oder mehrerer unter Versionskontrolle
    stehender Dateien auf die letzte Version zurück. +
    `git restore :/` – Verwirft alle Änderungen im Repository. +
    `git restore .` – Verwirft alle Änderungen im aktuellen Verzeichnis. +
    `git restore <file>` – Verwirft die Änderungen in den angegebenen Dateien
    oder Verzeichnissen.
<2> Ältere alternative Variante gegenüber `restore`.
<3> Alternative Möglichkeit zu `git restore :/`. Ein `--hard` veranlasst bei
    einem `git reset` auch den Workspace, also die lokalen (geänderten) Dateien,
    zurückzusetzen.
<4> Entfernt alle lokalen nicht unter Versionskontrolle stehenden Dateien.
    (https://git-scm.com/docs/git-clean[git-clean Dokumentation], `-n` Testlauf,
    `-i` interaktiv, `-d` beachte auch entsprechende Verzeichnisse, `-f` ignoriere
    Löschwarnung)
=====
====

==== Aufgabe 1.4 - Version verwerfen

. Nehmen Sie in Ihrem Repository eine Änderung als neue lokale Version auf.
  Schauen Sie sich die Versionshistorie an und nehmen Sie die eben gemachte
  Version mit `reset` zurück.
+
.Hinweise: `reset`
[%collapsible]
====
=====
Mit dem Befehl `reset` kann der aktuelle Stand des Repositorys auf eine frühere
Version (Commit) zurückgesetzt werden. Alle davon ausgehenden neueren Versionen
werden verworfen.

Die enthaltenen Änderungen bleiben im Arbeitsverzeichnis erhalten, wenn nicht
die Option `--hard` angegeben wird.

image::grafik_git_reset.png["...",width=490]

----
$ git add .
$ git commit -m "..."
$ git log --oneline
$ git reset --hard <commit> <1> <2>
----
<1> Setzt den aktuellen Stand des Repositorys auf die angegebe Version
    (Commit) zurück.
<2> Der Commit kann relativ `HEAD~1` oder absolut `a2a33b23` angegeben
    werden.
=====
====
+
IMPORTANT: Die Verwendung von `reset` ist nur für *lokale*, *private* oder noch
*nicht veröffentlichte* Versionen (Commits) geeignet. Denn das Verändern der
Repository-Historie führt, im Gegensatz zu `revert`, zu Problemen mit anderen
Nutzern, da die Versionskette nicht mehr synchron ist.

. Nehmen Sie in Ihrem Repository eine weitere Änderung als neue lokale Version
  auf. Schauen Sie sich die Versionshistorie an und nehmen Sie die eben
  gemachte Version diesmal mit `revert` zurück.
+
.Hinweise: `revert`
[%collapsible]
====
=====
Mit dem Befehl `revert` kann **eine** bestimmte Version (Commit) zurückgenommen
werden. Dabei wird eine neue Version erzeugt, die den aktuellen Stand ohne die
Änderung der zurückgenommenen Version enthält.

Die Versionshistorie bleibt inklusive der zurückgenommenen Version erhalten.

image::grafik_git_revert.png["...",width=593]

----
$ git add .
$ git commit -m "..."
$ git log --oneline
$ git revert <commit> <1>
----
<1> Nimmt die Änderung der angegebenen Version zurück und erzeugt eine neue
    Version (ohne die Änderung der zurückgenommenen Version).
=====
====
+
NOTE: Die Verwendung von `revert` erhält, gegenüber `reset`, die Versionskette
und ist konsistent zu *entfernten*, *öffentlichen* und *geteilten*
Repositories.

=== 2. Versionen ändern und zusammenfassen

[#warning1]
IMPORTANT: Das Ändern (`commit --amend`) und das Zusammenfassen (`rebase -i`)
von Versionen zu einer neuen Version verändern die Commit-ID(s) und die
Versionshistorie des Repositorys, ähnlich wie bei `reset`. Es ist nur für
*lokale*, *private* Repository und noch *nicht veröffentlichte* Versionen
empfohlen, um unterschiedliche Versionsketten mit anderen Nutzern zu vermeiden.

Falls der oder die ursprünglichen Commits schon in ein __remote__-Repository
gepusht wurden, muss der überschriebene Commit noch einmal mit `git push
--force` oder besser
https://git-scm.com/docs/git-push#Documentation/git-push.txt---no-force-with-lease[`git
push --force-with-lease`] gepusht werden. (obere <<#warning1,Warnung>>
beachten!)

.Hinweise: Force-Push mit VS Code
[%collapsible]
====
=====
In VS Code ist über das Git-Menü standardmäßig kein Force-Push möglich und man
kann nur über das integrierte Terminal `git push --force` ausführen.

Über die Einstellungen von VS Code: "Settings > Extensions > Git" kann die
Option *Allow Force Push* aktiviert werden. Danach sind im Git-Menü "...
> Pull, Push > " entsprechende *Push (Force)* Einträge vorhanden.
=====
====

==== Aufgabe 2.1 - letzte Version ändern

. Nehmen Sie in Ihrem Repository eine Änderung als neue lokale Version auf und
  schauen Sie sich die Versionshistorie an.

. Ändern Sie mit `commit --amend` die Commit-Message des eben erstellten
  letzten Commits. Alternativ nehmen Sie vorher eine lokale Änderung vor,
  welche mit in die Änderung des letzten Commits einfließen soll.

.Hinweise: `commit --amend`
[%collapsible]
====
=====
Der Zusatz `--amend` ist eine gute Möglichkeit, um Fehler in der Commit-Message
zu korrigieren oder vergessene Änderungen oder Dateien nachträglich
aufzunehmen.

image::grafik_git_commit_amend.png["...",width=393]

----
$ ...
$ git add .
$ git commit -m "... Message ..."
$ git log --oneline
$ ...
$ git add . <1>
$ git commit --amend -m "... (neue) Message ..." <2>
$ git log --oneline
----
<1> optional: Aufnahme der vergessenen/zusätzlichen Änderungen.
<2> Mit der Option `--amend` wird der letzte Commit mit dem aktuellen Commit
    überschrieben.
=====
====

[#aufgabe2-2]
==== Aufgabe 2.2 - Versionen zusammenfassen

. Nehmen Sie in Ihr Repository *drei* neue Versionen (Commits) auf.
. Fassen Sie mit `rebase -i` diese drei Commits zu einem neuen Commit
  zusammen.

.Hinweise: `rebase -i`
[%collapsible]
====
=====
Mit dem Befehl `rebase -i` können mehrere Commits nachträglich angepasst,
zusammengefasst oder gelöscht werden. Dabei wird die Versionshistorie verändert
und die Commit-IDs der zusammengefassten Commits ändern sich.

NOTE: Es werden nur die Commits nach dem angegebenen Commit verwendet. Git
arbeitet die Commits vom ältesten (oben) zum neuesten (unten) ab. Bei `squash`
und `fixup` wird der ausgewählte Commit mit dem direkt darüberstehenden
(älteren) Commit zusammengeführt.

image::grafik_git_rebase-i.png["...",width=435]

----
$ git log --oneline
00af044 (HEAD -> main) Fix typo in <object>
0af0043 Update <object>
af00042 Add new <object>
f000041 Fixup #11 <object>
...

$ git rebase -i HEAD~3 <1>
pick af00042 Add new <object>
f    0af0043 Update <object> <2>
f    00af044 Fix typo in <object> <2>

$ git log --oneline
f000045 (HEAD -> main) Add new <object>
...
----
<1> Alle neueren Commits nach dem angegebenen Commit (hier relativ) werden
    einzeln bearbeitet (siehe Tabelle). Alternative kann der Commit auch
    direkt per `$ git rebase -i f000041` angegeben werden.
<2> Die beiden Nachfolge-Commits (`00af044`, `0af0043`) werden mit `f` (fixup)
    statt `pick` markiert, um in den vorhergehenden Commit (`af00042`) aufgenommen
    zu werden. (Erst wird `0af0043` mit `af00042` zusammengeführt, danach
    `00af044` mit dem eben neu entstandenen Commit.)

.Rebase-Aktionen
[cols="1,1,5"]
|===
| Aktion   | Kurz | Beschreibung

| `pick`   | `p`  | Commit behalten (unverändert)
| `reword` | `r`  | Commit behalten, aber Commit-Message ändern
| `squash` | `s`  | Commit mit vorherigen Commit zusammenführen, inkl. Commit-Message
| `fixup`  | `f`  | Commit mit vorherigen Commit zusammenführen, ohne Commit-Message
|===

NOTE: Ist bei Ihnen im Terminal für Git der Editor vi(m) eingestellt, können
Sie mit kbd:[i] in den Bearbeitungsmodus wechseln und nach der Änderung mit
kbd:[Esc] und der Eingabe von `:wq` speichern und den Editor schließen.

=== Extras

==== checkout vs switch/restore

Der Befehl `git checkout` erfüllt mehrere unterschiedliche Aufgaben. Daher wurden
mit `git switch` und `git restore` spezialisierte Befehle eingeführt, die
deutlicher machen, ob ein Branch gewechselt oder eine Datei wiederhergestellt
werden soll.

.Moderne Alternativen zu git checkout
[cols="1,1"]
|===
| git checkout                 | Moderne Alternative

| git checkout <branch>        | git switch <branch>
| git checkout -b <branch>     | git switch -c <branch>
| git checkout <commit>        | git switch --detach <commit>
| git checkout -- <file>       | git restore -- <file>
| git checkout <commit> <file> | git restore --source=<commit> <file>
|===
