=== Was sind Branches?

Mit *Branches* (Verzweigungen) bietet Git die Möglichkeit, ausgehend vom
Hauptzweig, Versionen auf unterschiedlichen Zweigen zu erstellen. Diese
Versionen können mit anderen Branches zusammengeführt (`merge`), verworfen oder
bewusst getrennt gehalten werden.

.Beispielhaftes Branching
image::grafik_git_branching.png[Beispielhaftes Branching,width=495]

Mit Hilfe von Branching kann bspw. ein neues Feature oder ein Bugfix in einem
extra Branch entwickelt und getestet werden, ohne den Hauptzweig zu
beeinflussen. Nach Fertigstellung werden die Änderungen in den stabilen
Hauptzweig aufgenommen.

.Erklärung von `merge`
[%collapsible]
====
=====
*merge*

Wird der Versionsstand eines Branches in einen anderen Branch aufgenommen
(`merge`) geschieht dies entweder mit der **fast-forward**-Strategie oder der
**ort**-Strategie (früher *recursive*) Strategie.

_fast-forward_::
+
--
image::grafik_git_merge_fast-forward.png[...,width=549]

.Beispiel: Git-Kommandos
[%collapsible]
======
[source,sh]
----
# Create a new feature branch and switch to it
git switch -c feature
# Edit the feature file and commit changes
vi feature.txt
git add .
git commit -m "..."
# Edit the feature file and commit changes
vi feature.txt
git add .
git commit -m "..."
# Switch back to the main branch
git switch main
# Merge the feature branch into the main branch
git merge feature
----
======

Basiert der zu mergende Branch (__feature__-Branch) auf dem letzten Stand des
aktuellen Branches (__main__-Branch), liegen die letzten Versionen der beiden
Branches in einer direkten Nachfolge. Somit wird durch ein *fast-forward* der
Zeiger des aktuellen Branches (__main__-Branch) auf die letzte Version des zu
mergenden Branches (__feature__-Branch) bewegt. +
Möchte man keinen __fast-forward__-Merge, sondern immer einen neuen
__merge__-Commit haben, kann dies mit `--no-ff` erzwungen werden.
--

_ort_ (_recursive_)::
+
--
image::grafik_git_merge_recursive.png[...,width=602]

https://git-scm.com/docs/git-rebase.html#Documentation/git-rebase.txt-ort[ort]
ist ein 3-Wege-Merge mit einem __merge__-Commit und ersetzt den älteren
__recursive__-Algorithmus seit Git v2.34.0 (seit v2.49.0 ist _recursive_ ein
Synonym für _ort_).

.Beispiel: Git-Kommandos
[%collapsible]
======
[source,sh]
----
# Create a new feature branch and switch to it
git switch -c feature
# Edit the feature file and commit changes
vi feature.txt
git add .
git commit -m "..."
# Edit the feature file and commit changes
vi feature.txt
git add .
git commit -m "..."
# Switch back to the main branch
git switch main
# Edit the main file and commit changes
vi main.txt
git add .
git commit -m "..."
# Merge the feature branch into the main branch
git merge feature
----
======

Gibt es im aktuellen Branch (__main__-Branch) Versionen, die nach der Abspaltung
des zu mergenden Branches (__feature__-Branch) erstellt worden sind, wird beim
Merge im aktuellen Branch (__main__-Branch) eine neue Version (__merge__-Commit)
erstellt. Diese enthält das vereinte Ergebnis aus den letzten Versionen der zu
mergenden Branches.
--
=====
====

.Erklärung von `rebase`
[%collapsible]
====
=====
*rebase*

image::grafik_git_rebase.png[...,width=549]

Mit einem Rebase wird die Basis, auf der die Versionen in einem Branch
basieren, auf eine neuere Version aktualisiert.

.Beispiel: Git-Kommandos
[%collapsible]
======
[source,sh]
----
# Create a new feature branch and switch to it
git switch -c feature
# Edit the feature file and commit changes
vi feature.txt
git add .
git commit -m "..."
# Edit the feature file and commit changes
vi feature.txt
git add .
git commit -m "..."
# Switch back to the main branch
git switch main
# Edit the main file and commit changes
vi main.txt
git add .
git commit -m "..."
# Switch back to the feature branch
git switch feature
# Rebase the feature branch onto the main branch
git rebase main
----
======

Wird zusätzlich noch die Option `-i` verwendet, können die neu erstellten
Commits zusätzlich verändert und zusammengefasst werden. (Siehe:
<<07-git-advanced.adoc#aufgabe2-2, Aufgabe 2.2>>)

IMPORTANT: Ein Rebase erzeugt immer neue Versionen (Commits-IDs,
Commit-Inhalte) was in Verbindung mit öffentlichen und geteilten
Team-Repositories zu Problemen führen kann.

* Rebase ist hilfreich, wenn bspw. im __main__-Branch eine neue Version
  (__bugfix__-Commit) hinzukommt, welche für die weitere Bearbeitung im
  __feature__-Branch ebenfalls relevant ist.
* Ebenfalls kann es hilfreich sein, wenn man eine flache Historie im Repository
  haben möchte, so dass bei einem Merge statt eines __merge__-Commits ein
  __fast-forward__-Merge durchgeführt werden kann.
=====
====

.Vorteile von `merge` und `rebase`
[%collapsible]
====
=====
*`merge` (ort, `--no-ff`)*

* Führt zu einer verzweigten Historie, die die beteiligten Commits der Branches
  und deren Zusammenführung deutlich macht.
* Feature-Branches bleiben in der Historie erhalten und nachvollziehbar.
* Merge-Commits lassen sich einfacher per `revert` rückgängig machen.

*`merge` (fast-forward)*

* Führt zu einer linearen (flachen) Historie, wenn der zu mergende Branch auf
  dem letzten Stand des aktuellen Branches basiert.
* Variante, falls man keine Merge-Commits haben möchte.

*`rebase`*

* Aktualisiert die Basis des __aktuellen__-Branches auf die aktuelle Version des
  __basis__-Branches, was nachfolgende __fast-forward__-Merges erlaubt.
* Mit `-i` können Commits angepasst und zusammengefasst werden, um die Historie
  übersichtlicher zu gestalten oder Fehler zu korrigieren.
=====
====

.Hinweise: Aktualisierung eines Branches
[%collapsible]
====
=====
Der __feature__-Branch kann während seiner Bearbeitung wie folgt auf
zwischenzeitlich neuere Versionen im __main__-Branch aktualisiert werden.

.Variante 1: rebase __feature__-Branch auf __main__-Branch
[source,sh]
----
git switch feature
git rebase main
----

.Variante 2: merge __main__-Branch auf __feature__-Branch
[source,sh]
----
git switch feature
git merge main
----

* Für die Aktualisierung eines in der Version länger zurückliegenden oder mit
  einem alten Feature abgeschlossenen __feature__-Branches ist die Variante 2 mit
  einem Merge empfohlen.
* Ein Rebase des __feature__-Branches kann auch sinnvoll sein, um
  zwischenzeitliche neuere Versionen im __main__-Branch vor einem Merge in diesen
  im __feature__-Branch erst zu testen bzw. mögliche Konflikte zu lösen.
  Andernfalls fallen die Konflikte erst beim Merge in den __main__-Branch auf.
=====
====

.Unterschied von `local` und `remote`
[%collapsible]
====
=====
*local*

* Commits und Branches existieren nur im lokalen Repository und sind nur für
  den Benutzer sichtbar, der das Repository auf seinem Rechner verwaltet.
  Änderungen in einem lokalen Branch wirken sich nicht auf andere Benutzer oder
  das zentrale (remote) Repository aus, bis sie explizit in ein
  __remote__-Repository gepusht werden.
* Lokale Änderungen können so noch bearbeitet, getestet und überprüft werden, bevor sie
  in das zentrale Repository übernommen werden.
* Normales Vorgehen für rein lokale Repositories ohne zentrale (remote) Repositories.

*remote*

* Commits und Branches existieren in einem zentralen Repository (z.B. auf
  GitHub, GitLab, Bitbucket, etc.) und sind für alle Benutzer sichtbar, die
  Zugriff auf dieses Repository haben.
* Änderungen in einem __remote__-Branch wirken sich auf alle Benutzer aus, die
  dieses Repository klonen oder darauf zugreifen.
* Lokale Repositories müssen regelmäßig mit dem __remote__-Repository
  synchronisiert werden, um die neuesten Änderungen zu erhalten.
* Remote-Branches ermöglichen die Zusammenarbeit und das Teilen von Branches
  zwischen mehreren Benutzern in einem Team.
* Remote-Branches erlauben das Verwenden von Pull-Requests oder Merge-Requests,
  um Änderungen per Git-Workflow und Code-Reviews zu überprüfen und zu mergen.
=====
====

.Hilfreiche Branching-Kommandos
[cols="2,3"]
|===
| Kommando | Beschreibung

| `git branch`
| lokale Branches auflisten +
  `-r` remote Branches, `-a` local und remote Branches

| `git branch <new-branch>`
| Branch anlegen

| `git switch <branch> +
  git checkout <branch>`
| Branch wechseln

| `git switch -`
| Zum vorherigen Branch wechseln

| `git switch -c <new-branch> +
  git checkout -b <new-branch>`
| Branch anlegen und wechseln. Kurzform für `git branch <new-branch>` gefolgt
  von einem `git switch <new-branch>` oder `git checkout <new-branch>`.

| `git branch -d <branch>`
| Branch löschen (`-d` _merged_, `-D` _unmerged_)

| `git merge <branch>`
| Versionen aus <branch> in den aktuellen Branch aufnehmen.

| `git merge --no-ff <branch>`
| Kein _fast forward_ merge, sondern immer neuer merge-Commit

| `git rebase <branch>`
| Versionen aus dem aktuellen Branch auf die aktuelle Version von <branch>
  aktualisieren. Mit der Option `-i` können Commits angepasst und zusammengefasst
  werden.
|===

=== 2. Branches verwenden

==== Aufgabe 2.1 - Branches (_local_)

. Legen Sie ausgehend vom __main__-Branch einen neuen lokalen __feature__-Branch an
  und wechseln Sie in diesen (`git switch -c feature`). Ersetzen Sie im
  Abschnitt *Feature 1* den feature-Platzhalter mit neuem Text und nehmen Sie die
  Änderung als neuen Commit auf.
+
WARNING: Den eben angelegten __feature__-Branch nicht zu GitHub publizieren!

. Legen Sie ausgehend vom __main__-Branch (`git switch main`) einen neuen lokalen
  __bugfix__-Branch an und wechseln Sie in diesen (`git switch -c bugfix`).
  Ersetzen Sie im Abschnitt *Beschreibung* den bugfix-Platzhalter mit neuem
  Text und nehmen Sie die Änderung als neuen Commit auf.
+
WARNING: Den eben angelegten __bugfix__-Branch nicht zu GitHub publizieren!

. Jetzt übernehmen (mergen) Sie die Änderungen vom __bugfix__-Branch in den
  __main__-Branch (`git switch main`, `git merge bugfix`) und entfernen den
  __bugfix__-Branch (`git branch -d bugfix`). Synchronisieren Sie Ihre Änderung
  in Ihr __remote__-Repository (`git push`).

. Wechseln Sie in den __feature__-Branch (`git switch feature`).
+
Optional: Aktualisieren Sie den __feature__-Branch mit den neuen Änderungen aus
dem __main__-Branch per `git rebase main`.

. Fügen Sie in den Abschnitt *Feature 1* weiteren Text als neuen Commit ein.
  Nehmen Sie anschließend die Änderungen aus dem __feature__-Branch in den
  __main__-Branch ohne fast-forward-Merge (`git switch main`, `git merge --no-ff
  feature`) auf und entfernen den __feature__-Branch (`git branch -d feature`).

. Synchronisieren Sie Ihre Änderung in Ihr __remote__-Repository (`git push`).


==== Aufgabe 2.2 - Branches (_remote_)

Lokale Branches können auf einem __remote__-Repository bereitgestellt werden, so
dass diese öffentlich bzw. von Teammitgliedern mit genutzt werden können.

. Legen Sie in Ihrem Repository einen neuen lokalen __feature-x__-Branch an und
  wechseln Sie in diesen.

. Nehmen Sie in den __feature-x__-Branch ein paar Commits auf.

. Veröffentlichen Sie den lokalen __feature-x__-Branch auf Ihrem
  __remote__-Repository (`git push -u origin feature-x`).

. Übernehmen (mergen) Sie im lokalen Repository die Änderungen vom
  __feature-x__-Branch in den __main__-Branch und entfernen Sie anschließend den
  lokalen __feature-x__-Branch. Synchronisieren Sie Ihre Änderung in Ihr
  __remote__-Repository.

. Entfernen Sie jetzt den __feature-x__-Branch auf Ihrem __remote__-Repository
  (`git push origin --delete feature-x`).

.Hinweise: __remote__-Branches
[%collapsible]
====
=====
.Neuen __local__-Branch in das __remote__-Repository aufnehmen:
[source,sh]
----
git push -u origin <new_local_branch> <1>
----
<1> Nimmt einen neuen lokalen Branch `<new_local_branch>` in das
    __remote__-Repository (origin) auf und verbindet den lokalen Branch mit diesem.

.Neuen __remote____-Branch in das lokale Repository aufnehmen:
[source,sh]
----
git pull <1> <2>
git switch <new_remote_branch> <3>
----
<1> lokalen Stand vom __remote__-Repository aktualisieren
<2> Alternativ geht auch ein `git fetch`, wenn man nur neue Branches und
    Versionen laden möchte, ohne diese schon mit dem Arbeitsverzeichnis zu mergen.
<3> In den neuen __remote__-Branch wechseln. Da er lokal nicht vorhanden ist,
    wird automatisch ein gleichnamiger _lokaler_ Branch angelegt und mit dem
    __remote__-Branch verbunden.

.__local__-Branch und __remote__-Branch synchronisieren:
[source,sh]
----
git pull <1>
git pull origin <branch> <2>

git push --all <3>
git push <4>
git push origin <branch> <5>
----
<1> Lade alle Änderungen von remote Branches, welche mit lokalen verbunden sind.
<2> Lade nur `<branch>` Änderungen vom __remote__-Repository `origin`.
<3> Sende alle Änderungen von __local__-Branches, welche mit __remote__-Branches
    verbunden sind.
<4> Sende alle Änderungen vom aktuellen __local__-Branch, wenn er mit einem
    __remote__-Branch verbunden ist.
<5> Sende alle Änderungen vom __local__-Branch `<branch>`, wenn er mit einem
    __remote__-Branch auf dem __remote__-Repository `origin` verbunden ist.

.__remote____-Branch löschen:
[source,sh]
----
git push <remote-repo> --delete <remote-branch> <1>
----
<1> Löscht den <remote-branch> auf dem <remote-repo>. In der Regel lautet der
    <remote-repo> Name _origin_.

.Veraltete Referenzen entfernen:
Sind die Branches remote und lokal gelöscht, aber ein `git branch -a` listet
noch veraltete Referenzen zu __remote__-Branches auf, können Sie wie folgt
entfernt werden:
[source,sh]
----
git remote prune origin
----

=== Extras

==== Branch-Namen

Verwendet man mehrere Branches im Repository, ist es sinnvoll *aussagekräftige
Namen* zu verwenden und im Team entsprechende *Namenskonventionen* festzulegen.

.Namen mit Trennzeichen:
Namen könnten mit einem Wort für die Art des Branches beginnen gefolgt von
spezifischen Informationen. Trennzeichen für eine bessere Lesbarkeit könnten
`-` und `_` sein.

* Art: `hotfix-`, `fix-`, `bugfix-`, `feature-`, `update-`, `test-`, etc.
* Info: `feature-pdf-generation`, `bugfix-issue-12`, `update-js-framework`, etc.

.Namen mit hierarchischer Struktur:
Eine weitere Variante wäre mit Hilfe von `/` (forward slash) hierarchische
Branch-Namen zu verwenden. So könnten bspw. mit `+git branch --list
'feature/*'+` oder `+git show-branch 'feature/*'+` alle vorhandenen bzw.
Commits zu den __feature__-Branches aufgelistet werden.

* Bspw.: `feature/pdf-generation`, `bugfix/issue-12`, `bugfix/issue-15`, etc.
* Einige Clients bilden die Branches dann auch als navigierbare Struktur ab:
+
[source,txt]
----
├── bugfix
│   ├── issue-12
│   └── issue-15
├── feature
│   ├── pdf-generation
│   └── xyz
└── main
----

WARNING: Branch-Namen dürfen nicht mit einem `/` enden.

==== Beispielhafte Anwendung

Das Repository befindet sich im __main__-Branch. Für ein neues Feature und einen
zwischenzeitlichen Bugfix werden ein temporärer __feature__-Branch und ein
__bugfix__-Branch verwendet.

. __feature__-Branch vom __main__-Branch erstellen und in diesen wechseln:
+
[source,sh]
----
git switch -c feature
----

. Feature bearbeiten und als neuen Commit in den __feature__-Branch aufnehmen:
+
[source,sh]
----
vi feature.txt
git add .
git commit -m "add ..."
----

. In den __main__-Branch zurück wechseln und __bugfix__-Branch vom diesem aus
  erstellen und hin wechseln:
+
[source,sh]
----
git switch main
git switch -c bugfix
----

. Bugfix bearbeiten und als neuen Commit in den __bugfix__-Branch aufnehmen:
+
[source,sh]
----
vi main.txt
git add .
git commit -m "fix ..."
----

. In den __main__-Branch zurück wechseln. Anschließend die Änderungen vom __bugfix__-Branch in
  diesen aufnehmen (standardmäßig fast-forward-Merge) und anschließend den __bugfix__-Branch
  löschen:
+
[source,sh]
----
git switch main
git merge bugfix
git branch -d bugfix
----

. In den __feature__-Branch wechseln. Anschließend den __feature__-Branch per
  `rebase` auf den aktuellen Stand des __main__-Branches aktualisieren:
+
[source,sh]
----
git switch feature
git rebase main
----

. Feature weiter bearbeiten und als neuen Commit in den __feature__-Branch
  aufnehmen:
+
[source,sh]
----
vi feature.txt
git add .
git commit -m "update ..."
----

. In den __main__-Branch zurück wechseln. Anschließend die Änderungen vom
  __feature__-Branch mit einem Merge-Commit (`--no-ff`) in diesen aufnehmen und
  anschließend den __feature__-Branch löschen:
+
[source,sh]
----
git switch main
git merge --no-ff feature
git branch -d feature
----

==== Standardverhalten konfigurieren

Git bietet die Möglichkeit, das Standardverhalten von `pull`, `rebase` und
`merge` zu konfigurieren.

..gitconfig
[source,ini]
----
[pull]
    rebase = true <1>

[rebase]
    autoStash = true <2>

[merge]
    ff = true <3>
    conflictStyle = zdiff3 <4>

[core]
    editor = "code --wait" <5>
----
<1> Bei `git pull` und wenn es neue Commits im Remote-Branch gibt, wird bei: +
    `false`: einen *Merge* durchgeführt (default) +
    `true`: ein *Rebase* durchgeführt
<2> `true`: Bei einem Rebase werden automatisch alle uncommitteten Änderungen
    zwischengespeichert (gestasht) und nach dem Rebase wiederhergestellt.
<3> Bei `git merge <branch>` wird bei: +
    `true`: wenn möglich, ein *fast-forward* Merge durchgeführt (default) +
    `false`: immer einen *Merge* mit einem neuen Merge-Commit durchgeführt,
    auch wenn ein *fast-forward* möglich wäre
<4> Legt den Stil der Konfliktmarkierungen bei einem Merge-Konflikt fest.
    https://git-scm.com/docs/git-merge/2.38.0#_how_conflicts_are_presented[`zdiff3`]
    wurde mit Git 2.35 eingeführt.
<5> Legt den Standard-Editor für Git-Kommandos fest.
