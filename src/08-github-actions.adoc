=== Einführung in GitHub Actions

"GitHub Actions makes it easy to automate all your software workflows, now with

-- https://github.com/features/actions[Quelle: GitHub Actions]

==== GitHub Actions

Mit *GitHub Actions* können zusätzlich zu im Repository gehostetem und
versioniertem Quellcode Softwareentwicklungsprozesse in *Workflows*
automatisiert werden. Diese sind auch unter dem Begriff *CI/CD* (_Continuous
Integration, Continuous Delivery/Deployment_) bekannt. Damit können bspw.
Tests, Buildvorgänge und das Bereitstellen der Software automatisiert werden.

Neben selbst erstellten Workflows, bieten GitHub und die Community eine
Vielzahl von vorgefertigten Workflows und Actions an.

Informationen findet man in der offiziellen Dokumentation:

- https://docs.github.com/en/actions[GitHub Actions]
- https://docs.github.com/en/actions/learn-github-actions/introduction-to-github-actions[Introduction to GitHub Actions]

==== Workflows

[#diagram_github-actions]
plantuml::{plantumlsdir}/diagram_github-actions.puml[format=svg, alt="Aufbau von Workflows in GitHub Actions", title="Aufbau von Workflows in GitHub Actions", target="{diagramsdir}/diagram_github-actions"]

Zu einem Repository können mit Hilfe von *GitHub Actions* verschiedene
*Workflows* hinzugefügt werden. *Workflows* werden durch festgelegte *Events*
ausgelöst. *Workflows* bestehen aus einem oder mehreren *Jobs*, welche wiederum
aus einem oder mehreren *Steps* bestehen. Die *Steps* enthalten jeweils eine
*Action*. Jobs laufen standardmäßig parallel ab und Steps werden immer der
Reihe nach ausgeführt.

GitHub Actions::
    GitHub Actions ermöglichen es zum Repository ein oder mehrere Workflows
    anzulegen und zu automatisieren.

Workflow::
    Ein Workflow ist ein zum Repository gehörender automatisierter Prozess,
    welcher in einer Datei mit YAML-Syntax unter `.github/workflows/`
    beschrieben wird. Workflows bestehen aus einem oder mehreren Jobs und
    können durch ein Ereignis ausgelöst werden. Man kann sie zum Erstellen
    (_build_), Testen (_test_), Packen (_package_), Freigeben (_release_) oder
    Bereitstellen (_deploy_) eines Projekts auf GitHub verwenden.

Event::
    Ein Event bzw. Ereignis ist eine bestimmte Aktivität, welche einen Workflow
    auslöst. Beispielsweise ein auf GitHub erfolgter Push oder Pull-Request.

Job::
    Ein Job besteht aus einer Reihe von Schritten (_Steps_), die auf demselben
    Runner ausgeführt werden. Mehrere Jobs in einem Workflow werden
    standardmäßig parallel ausgeführt. Es können zusätzlich Abhängigkeiten
    definiert werden, sodass sie nacheinander bzw. in festgelegter Reihenfolge
    ausgeführt werden können.

Runner::
    Ein Runner ist eine virtuelle Umgebung bzw. spezieller Server in dem ein
    Job ausgeführt wird. Nach Beendigung des Jobs meldet der Runner den
    Fortschritt, die Protokolle und die Ergebnisse an GitHub zurück. Von GitHub
    gehostete Runner basieren auf Ubuntu Linux, Microsoft Windows und macOS und
    jeder Job in einem Workflow wird in einer neuen virtuellen Umgebung
    ausgeführt.

Step::
Ein Step bzw. Schritt ist eine einzelne Aufgabe in einem Job, welche der Reihe
nach ausgeführt wird. Ein Schritt kann entweder eine Aktion oder ein
Shell-Befehl sein. Jeder Schritt in einem Job wird auf demselben Runner
ausgeführt, sodass sie Daten miteinander teilen können.
+
[IMPORTANT]
====
Ob ein Step erfolgreich war, entscheidet der Exit-Code der Action. Tritt ein
Fehler (`exit code != 0`) auf, werden standardmäßig keine nachfolgenden Steps
mehr bearbeitet und der Job wird mit einem negativen Ergebnis beendet.
====

Action::
    Eine Action ist ein eigenständiger Befehl, der zu einem Step gehört.
    Actions sind die kleinsten Teile eines Workflows. Diese können
    Shell-Kommandos (`run:`) oder von GitHub bzw. der Community vorbereitete
    Actions (`uses:`) sein.

Die Workflow-Dateien liegen im Repository unter dem Verzeichnis
`.github/workflows/` im https://yaml.org/spec/1.2/spec.html[YAML]-Format. Jeder
Workflow wird durch eine Datei mit der Endung _.yaml_ oder _.yml_, bspw.
_example.yaml_, beschrieben.

.Hinweise: Workflows Syntax in einer YAML-Datei
[%collapsible]
====
=====
Ausführliche Hinweise zur Syntax findet man unter:
https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax[Workflow syntax for GitHub Actions].

.example.yaml
[source, yaml]
----
name: My Workflow <1>
on: [push, pull_request] <2>
jobs: <3>
  test: <4>
    name: My Tests <5>
    runs-on: ubuntu-latest <6>
    env: <7>
      MY_FILE: README.md

    steps: <8>
      # step 1 - action <9>
      - name: Checkout the repository <10>
        uses: actions/checkout@v7 <11>

      # step 2 - single line shell command
      - name: Check file
        working-directory: folder/subfolder <12>
        run: test -f "$MY_FILE" <13>

      # step 3 - multi line shell command
      - name: Check versions
        run: | <14>
            echo "check versions:"
            git --version
            java -version
----
<1> `name: <workflow_name>` Name des Workflows
<2> `on:` Das Event (Ereignis), welches den Workflow auslöst. Dies kann
    auch gezielt auf Branches oder Dateien/Verzeichnisse eingeschränkt werden.
    Siehe <<example_event>>.
<3> `:jobs:` Bereich für alle Jobs in diesem Workflow
<4> `<job_id>:` Erster Job mit der eindeutigen ID "test" im Jobs-Bereich
<5> `name: <job_name>` Legt den Namen eines Jobs fest.
<6> `runs-on:` Definiert den Runner mit seiner Umgebung `ubuntu-latest` für
    den zugehörigen Job. In diesem Falle die von GitHub gehostete virtuelle
    Umgebung mit Ubuntu Linux.
<7> `env:` Hier können Umgebungsvariablen, bspw. `MY_FILE` definiert
    werden, welche in den Steps verwendet werden.
<8> `steps:` Bereich für alle Schritte zu einem Job.
<9> `#` Kommentar
<10> `- name: <step_name>` Legt den Namen eines Steps fest.
<11> `uses: <action>` Eine spezielle Action `actions/checkout@v7`, welche
     den Inhalt des Repositories in den Runner lädt, so dass nachfolgende Actions
     damit arbeiten können.
<12> `working-directory: <path>` Legt das Arbeitsverzeichnis für den Step fest.
     Besser lesbar als `cd <path>`, da das Arbeitsverzeichnis explizit für den
     Step definiert wird.
<13> `run: <shell_command>` Führt statt einer vorgegebenen Action ein
     *einzeiliges* Shell-Kommando aus.
<14> `run: |` Führt ein *mehrzeiliges* Shell-Kommando aus.

[%collapsible]
====
=====
Weitere Hinweise zur Syntax findet man unter:

* https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax[Workflow syntax for GitHub Actions]
* https://yaml.org/spec/1.2/spec.html[YAML 1.2]
* https://en.wikipedia.org/wiki/YAML[Wikipedia: YAML]

.YAML-Grundelemente
[source,yaml]
----
# Kommentare beginnen mit #

# Einfaches Schlüssel-Wert-Paar
# Schlüssel: runs-on
# Wert: "ubuntu-latest"
runs-on: ubuntu-latest

# Sequenz (Liste) als Blockform
# Der Wert von "on" ist eine Liste mit zwei Elementen
on:
  - push
  - pull_request

# Dasselbe als Flow-Style (Kurzform)
on: [push, pull_request]

# Mapping (Sammlung von Schlüssel-Wert-Paaren)
# Der Wert von "on" ist hier ein Mapping.
# push und pull_request sind Schlüssel mit dem Wert null.
on:
  push:
  pull_request:

# Mapping mit verschachtelten Schlüssel-Wert-Paaren
jobs:
  test:
    runs-on: ubuntu-latest
----

.Mehrzeilige Strings
[source,yaml]
----
run: |
  echo "Zeile 1"
  echo "Zeile 2"
----

.Quotes und Sonderzeichen
[source,yaml]
----
env:
  FILE_NAME: "README.md"
  GREETING: 'Hello World'
  JSON: '{"name":"test","ok":true}'
----

.Wichtige Regeln
[source,yaml]
----
# 1. YAML arbeitet mit Einrückung
# 2. Verwenden Sie Leerzeichen, keine Tabs
# 3. Der Doppelpunkt trennt Schlüssel und Wert
# 4. Mehrzeilige Blöcke werden mit | geschrieben
# 5. Einrückung muss innerhalb eines Blocks konsistent sein
----

        run: |
          ls ${{ github.workspace }}
      - run: echo "🍏 This job's status is ${{ job.status }}."
----

Als Grundlage verwenden wir das bereitgestellte

. Erstellen Sie sich vom Repository-Template
  {exercise-repo-url}[{exercise-repo-name}] ein Repository in Ihrem
  GitHub Account und klonen es anschließend lokal auf Ihren Rechner.
. Legen Sie sich im Verzeichnis `.github/workflows/` entweder eine neue

. Übernehmen Sie entsprechend folgenden Inhalt:
+
.java-unit-tests.yaml
[%collapsible]
====
[source,yaml]
----
# This workflow will test a Java project with Maven
# See also: https://docs.github.com/en/actions/tutorials/build-and-test-code/java-with-maven

name: Unit tests with Maven

on:
  push:
    branches: [main]
    paths:
      - 'example-java/**'
  pull_request:
    branches: [main]
    paths:
      - 'example-java/**'

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
    # step 1 - clone project
    - name: Checkout the repository
      uses: actions/checkout@v7

    # step 2 - provide java
    - name: Set up JDK 21
      uses: actions/setup-java@v5
      with:
        distribution: 'temurin'
        java-version: '21'
        cache: 'maven'

    # step 3 - run tests
    - name: Test with Maven
      working-directory: example-java
      run: mvn -B test
----
====
+
.python-unit-tests.yaml
[%collapsible]
====
[source,yaml]
----
# This workflow will test a Python project
# See also: https://docs.github.com/en/actions/tutorials/build-and-test-code/python

name: Unit tests with Python

on:
  push:
    branches: [main]
    paths:
      - 'example-python/**'

    branches: [main]
    paths:
      - 'example-python/**'

.rust-unit-tests.yaml
[%collapsible]
====

  push:
    branches: [main]

      - 'example-rust/**'
